Onde eu ajustaria (pontos de atenção)
1. Haystack como orquestrador principal
Haystack 2.x/3.x é excelente para pipelines de produção limpos, tipados e observáveis. Em 2026 ele melhorou bastante o suporte a agents e tool calling.
Porém, para ciclos agentivos complexos (loops, branching, estado de longa duração, multi-hop, human-in-the-loop), a maioria das avaliações atuais coloca:

LangGraph como o mais forte em orquestração agentiva (estado tipado, checkpointing, time-travel debugging).
LlamaIndex Workflows como o melhor quando o gargalo é qualidade de retrieval sobre documentos.
Haystack como o mais “enterprise/pipeline-oriented”.

Recomendação prática para o seu caso:

Se você quer simplicidade e pipelines bem definidos → Haystack é uma escolha válida e defensável.
Se você prevê agentes mais sofisticados (várias ferramentas em sequência, replanejamento, memória de longo prazo complexa) → considere LangGraph como orquestrador e use Haystack ou LlamaIndex apenas como componentes de retrieval.

Você pode misturar: LangGraph orquestra + Haystack/LlamaIndex como “ferramentas de RAG”.
2. Modelo local + tool calling
Isso é crítico. Nem todo modelo de 35B MoE tem tool calling de qualidade. Modelos da família Qwen3 / Qwen3.5 / Qwen3.6 (especialmente as variantes A3B) estão entre os melhores locais para function calling em 2026. Modelos mais antigos ou pouco treinados em tools costumam alucinar parâmetros ou chamar a ferramenta errada.
Com sua RTX 4060 + 64 GB RAM, o caminho mais realista é:

Quantização forte (Q4/Q5)
Offload agressivo de especialistas para RAM
Servidor OpenAI-compatible (llama.cpp, vLLM, SGLang ou Ollama)

Por que esta combinação (e não outras)

LangGraph em vez de Haystack puro
Haystack é excelente para pipelines limpos e tipados. LangGraph é superior quando o sistema precisa de raciocínio multi-etapas, replanejamento e estado de longa duração. Você pode usar componentes de retrieval do Haystack ou LlamaIndex dentro do LangGraph se quiser.
PostgreSQL + Qdrant (híbrido)
Vetorial sozinho não resolve filtros complexos, histórico e auditoria. Relacional sozinho é fraco em busca semântica. A combinação cobre os dois mundos com qualidade.
OpenWebUI + API OpenAI-compatible
Desacopla a interface do backend. Você pode trocar o modelo ou o servidor de inferência sem reescrever a UI.
Foco forte no pipeline de ingestão
Com 1.000–2.000 PDFs, a qualidade da extração e do chunking importa mais do que o framework de orquestração. Por isso a arquitetura separa claramente a ingestão (offline) da consulta (online).

Detalhamento por Camada
Primeira Camada: Interface do Usuário (OpenWebUI)

O OpenWebUI atua como ponto de entrada unificado, com suporte a múltiplos usuários, histórico de conversas, upload de documentos e gestão de bases de conhecimento. Ele se comunica com a camada inferior via API compatível com OpenAI, podendo conectar-se simultaneamente ao llama-server local e a provedores remotos como OpenRouter. O usuário troca entre modelo local e modelos na nuvem na mesma interface.

Segunda Camada: API Gateway (Hayhooks)

O pipeline do Haystack não pode ser chamado diretamente pelo OpenWebUI — é preciso uma camada de "empacotamento". O Hayhooks resolve exatamente isso: ele implanta um Pipeline ou Agent do Haystack como API REST e expõe automaticamente um endpoint /chat/completions compatível com OpenAI. Isso significa que o "modelo" que o OpenWebUI enxerga é, na verdade, o seu Agente Haystack, e não um LLM cru. Esse é o ponto-chave para o comportamento agêntico — o modelo passa por um loop de chamadas de ferramentas antes de gerar a resposta final.

Terceira Camada: Núcleo de Orquestração (Haystack Agent)

O Haystack oferece o componente Agent, que já traz embutido o loop ReAct: o LLM gera resposta → se houver tool call → o ToolInvoker executa a ferramenta → o resultado volta ao LLM → repete até não haver mais necessidade de ferramentas ou até atingir o número máximo de passos. As ferramentas que você precisa definir incluem:

qdrant_search: busca semântica, retorna trechos relevantes dos documentos

postgres_query: consulta dados estruturados (estado de tarefas, histórico, metadados)

pdf_reader: lê sob demanda páginas ou seções específicas do PDF original

external_api: chama serviços externos (para expansão futura)

A definição das tools usa a abstração Tool ou ComponentTool do Haystack, e a descrição precisa deixar claro quando usar cada ferramenta.

Quarta Camada: Inferência de Modelos (Trilha Dupla)

Trilha local: llama-server rodando o Qwen3.6-35B-A3B, com quantização mista (camadas de especialistas em Q2_K, camadas GPU em Q4_K), usando --n-cpu-moe para descarregar os especialistas nos 64GB de RAM. Seu Ryzen 7 5700G + 64GB é mais que suficiente. Com 8GB de VRAM, recomendo quantização IQ3_M ou Q3_K_M (arquivo de 16-17GB), e a versão calibrada com iMatrix tem qualidade mais estável.

Trilha externa: via KTRouter ou proxy de roteamento local similar, que gerencia APIs externas como OpenRouter de forma unificada. O KTRouter expõe um endpoint local compatível com OpenAI, traduz automaticamente o formato da requisição e encaminha ao provedor configurado, com suporte a failover e estatísticas de uso.

Quinta Camada: Dados e Armazenamento

Componente	Papel	Justificativa

Fluxo de Dados do Loop Agêntico
Usuário digita a pergunta no OpenWebUI

Requisição chega ao /chat/completions do Hayhooks

O Agente Haystack monta system prompt + definições de ferramentas + histórico da conversa

O LLM (local ou externo) retorna resposta, possivelmente com tool_calls

O ToolInvoker do Haystack analisa e executa as chamadas (consulta Qdrant / PostgreSQL / lê PDF)

O resultado da ferramenta é anexado à conversa como nova mensagem

Volta ao passo 4, até o LLM retornar resposta em texto puro

A resposta é transmitida via streaming ao OpenWebUI, enquanto o Langfuse registra o trace completo

Vantagens Centrais desta Arquitetura
Entrada unificada, inferência dupla. O usuário vê uma única interface, uma única API. O backend decide automaticamente, com base em complexidade, privacidade e custo, se usa modelo local ou externo. O modelo local cuida de consultas simples e dados sensíveis; o externo, de raciocínio complexo e contextos longos.

Capacidade realmente agêntica. Não é o simples "busca → concatena → gera", mas o modelo decidindo ativamente quando chamar qual ferramenta. O componente Agent do Haystack suporta nativamente esse loop, e o Langfuse permite ver a trajetória completa de cada decisão.

Local primeiro, nuvem como fallback. Sua RTX 4060 + 64GB de RAM dá conta do dia a dia de perguntas e respostas sobre documentos e chamadas de ferramentas. Quando surge uma pergunta além da capacidade local, a camada de roteamento troca automaticamente para o OpenRouter. É a solução mais econômica: 80% do tráfego vai para o local (custo zero), 20% das consultas complexas vão para a nuvem (pago por uso).

Observabilidade embutida. A integração Langfuse + Haystack captura automaticamente entrada e saída de cada chamada de LLM, parâmetros e resultados de cada ferramenta, documentos e scores de cada etapa de retrieval. Você pode filtrar traces por nome de ferramenta, usuário ou sessão, localizando gargalos ou problemas de qualidade.

Expansão gradual. No início, rode apenas modelo local + Qdrant + Haystack. Depois, conforme necessário, adicione PostgreSQL (persistência de estado), KTRouter (roteamento multi-provider) e Langfuse (monitoramento de produção). Cada camada pode ser substituída ou atualizada de forma independente.

Diferenças-Chave em Relação a Outras Soluções
O que distingue esta arquitetura de um "sistema RAG" comum é o seguinte: tanto a decisão de roteamento quanto a decisão de chamada de ferramentas são delegadas ao próprio modelo, em vez de ficarem hardcoded na lógica do pipeline. O componente Agent do Haystack deixa o LLM decidir "essa pergunta precisa consultar o banco vetorial?", "preciso ler o PDF original?", "devo consultar o PostgreSQL antes para confirmar o estado?". Essa dinamicidade é a essência do agentic, e é o verdadeiro significado daquele "loop" que você descreveu.

Se você decidir seguir nesta direção, o próximo passo pode ser começar pelo template de quickstart do Hayhooks, fazer funcionar um Agent com uma única ferramenta (busca no Qdrant) e depois ir adicionando as demais ferramentas e a camada de roteamento.

Proposta do Qwen:

Proposta de Arquitetura: HARA (Hybrid Agentic RAG Architecture)
Abaixo apresento uma proposta formal de arquitetura, estruturada como um documento técnico que você pode usar como baseline para comparação com outras soluções.
1. Visão Geral
A HARA é uma arquitetura de IA corporativa híbrida que combina:
Inferência local (privacidade, custo zero, soberania de dados)
Inferência remota (velocidade, modelos de ponta, resiliência)
Memória dual (vetorial + relacional + grafo)
Orquestração agêntica com observabilidade de ponta
Ela é projetada para o cenário de 2.000+ PDFs, com extração determinística, raciocínio complexo e integração com sistemas corporativos (IBM Maximo, ERPs).
2. Princípios de Design (Os "Porquês" Macro)
Princípio
Motivo
Soberania de Dados por Padrão
Dados sensíveis nunca saem do ambiente local, a menos que explicitamente roteados.
Separação entre Dados, Razão e Ação
O LLM não armazena dados (faz só raciocínio). O estado vive em bancos. As ações vivem em ferramentas isoladas.
Orquestração sobre Framework
Preferimos pipelines explícitos (Haystack/LangGraph) a "caixas mágicas" que escondem o fluxo.
Observabilidade Nativa
Todo token, toda chamada de ferramenta, todo custo é rastreado. Sem Langfuse, não há produção.
Resiliência Híbrida
O sistema nunca fica 100% indisponível. Se o local cai, o remoto assume, e vice-versa.
Custo Proporcional à Complexidade
Tarefas simples rodam local. Tarefas complexas pagam centavos no OpenRouter.

6. Justificativas Técnicas (O "Porquê" de Cada Escolha)
Por que Qwen 2.5 32B e não Llama 3 ou Mistral?
Melhor desempenho em tool calling entre modelos open-weights.
Suporte nativo a contextos longos (128k).
Excelente em português (treinado em dados multilíngues).
Tamanho ideal para caber no seu hardware com Split Offloading.
Por que Haystack e não LangChain?
Haystack 2.x é baseado em pipelines orientados a dados, não em chains arbitrários.
Mais estável, menos breaking changes, melhor para produção.
Documentação técnica superior e comunidade corporativa.
Por que LangGraph para o agente e Haystack para o RAG?
LangGraph é especializado em grafos de estado (loops, condicionais, memória).
Haystack é especializado em pipelines de recuperação (indexação, busca, reranking).
Separar as responsabilidades evita o "canivete suíço" que vira uma bagunça.
Por que LiteLLM como proxy?
Unifica APIs (Ollama, OpenRouter, Anthropic, OpenAI) sob um único padrão OpenAI.
Permite fallback automático, load balancing e rate limiting sem reescrever código.
Seu LangGraph fala com um endpoint, não com cinco.
Por que Qdrant e não Chroma ou Milvus?
Chroma é ótimo para protótipos, mas escala mal para milhões de vetores.
Milvus é poderoso, mas complexo de operar (exige etcd, MinIO, etc.).
Qdrant tem o melhor equilíbrio: performance, filtros híbridos, facilidade de operação via Docker.
Por que Neo4j (GraphRAG)?
RAG vetorial puro falha em perguntas do tipo "quem se relaciona com quem" ou "trace o caminho entre A e B".
Grafos capturam relações que embeddings perdem.
Essencial para os 2.000 PDFs, que provavelmente têm entidades interconectadas.
Por que Langfuse?
Agentes são não-determinísticos. Sem observabilidade, você não sabe por que o agente errou.
Langfuse mostra: qual ferramenta foi chamada, com quais parâmetros, quanto custou, quanto demorou.
É o "gravador de voo" do seu sistema.
Por que Split Offloading no seu hardware?
RTX 4060 tem 8GB VRAM. Qwen 32B Q4 precisa de ~20GB.
Com 64GB de RAM, você pode colocar as camadas "quentes" (attention) na GPU e o resto na RAM.
Resultado: modelo de 32B rodando localmente, com custo zero por token, a ~5-8 tokens/segundo.

9. Diferenciais desta Arquitetura
Hibridismo Inteligente: Não é "tudo local" (lento, limitado) nem "tudo na nuvem" (caro, inseguro). É o melhor dos dois mundos, roteado automaticamente.
Memória Tripla: Vetorial (Qdrant) + Relacional (Postgres) + Grafo (Neo4j). Cobre 100% dos tipos de consulta.
Observabilidade Nativa: Langfuse não é um "extra", é parte do core.
Tool Calling de Verdade: Não é só RAG. É um agente que executa código, consulta ERPs, faz buscas determinísticas.
Otimizada para o Seu Hardware: Aproveita os 64GB de RAM com Split Offloading, algo que a maioria das arquiteturas ignora.
10. O Que Esta Arquitetura NÃO É
Para evitar expectativas irreais:
Não é um sistema de tempo real (latência de segundos a minutos em consultas complexas).
Não é um substituto de banco de dados tradicional (é uma camada de inteligência sobre eles).
Não é 100% determinística (LLMs são estocásticos por natureza; o Langfuse ajuda a controlar isso).
Não é "plug-and-play" (exige configuração, tuning de prompts, ajuste de chunking).
📌 Resumo em Uma Frase
HARA é uma arquitetura agêntica híbrida que usa seu hardware local para privacidade e custo zero, modelos remotos para raciocínio de ponta, memória tripla para cobertura total de consultas, e observabilidade nativa para produção confiável — orquestrada por Haystack + LangGraph e unificada por LiteLLM.
Quando você for comparar com outras propostas, use os 10 critérios da Seção 8 como régua. Se quiser, posso detalhar qualquer camada específica (ex: o grafo do LangGraph, o config.yaml do LiteLLM, ou o pipeline de ingestão do Haystack) para você ter ainda mais elementos de comparação.

OpenRouter fornece capacidade externa quando fizer sentido.
Langfuse permite descobrir o que realmente está acontecendo.
OpenWebUI fornece a interface.
FastAPI transforma tudo isso em uma plataforma, e não apenas um experimento.

E, principalmente, a arquitetura respeita a característica mais importante descoberta na amostra: seu problema não é simplesmente RAG sobre PDFs; é transformar publicações documentais compostas em uma base estruturada de atos, entidades, eventos e relações, e depois permitir que o agente raciocine sobre essa base. A análise da amostra inclusive já apontava que uma edição de 23 páginas pode conter mais de 40 atos, tornando inadequado simplesmente enviar a edição inteira para a LLM.

Esse, para mim, deve ser o princípio central do projeto.

O modelo

Confirmei que o Qwen3.6-35B-A3B existe. É um modelo open-weight da Alibaba lançado em abril de 2026, com 35B de parâmetros totais e cerca de 3B ativos por token. Ele tem 256 especialistas e janela de contexto de 262K tokens. Combina atenção linear com MoE esparso e suporta chamada de funções. Isso serve para agentes, e a atenção híbrida deve deixar o cache de contexto mais barato que o de um modelo denso. 
Qwen3.6 35B A3B +2

Como rodar na 4060 (assumindo 8 GB de VRAM):

Use llama.cpp (llama-server) com quantização Q4 (cerca de 20 a 22 GB no total) e a flag --jinja para o tool calling funcionar.
Deixe na GPU a atenção, os especialistas compartilhados e o KV cache. Mande os tensores dos especialistas roteados para a RAM, com --n-cpu-moe N ou -ot ".ffn_.*_exps.=CPU". Ajuste o N até a VRAM ficar quase cheia.
Vale comparar com o ik_llama.cpp e o KTransformers, que são mais agressivos em offload híbrido de MoE.
Seu Ryzen 5700G tem iGPU. Ligue o monitor nela para liberar 100% da VRAM da 4060.
Minha expectativa é algo entre 15 e 30 tokens/s de geração, limitado pela banda da RAM DDR4. É estimativa, então meça no seu setup. O gargalo real é o prefill, a leitura de prompts longos, que é lento com especialistas na CPU.
Os cinco ajustes
Não use o LLM local para ingerir os 2.000 PDFs. Parsing, embeddings e reranking devem ser feitos por modelos especializados e pequenos. O LLM entra só para extração de metadados, em lote noturno, com saída estruturada (JSON schema).
O roteador precisa de política de dados, não só de custo. Se o OpenRouter receber trechos de documentos sensíveis, eles saem da sua máquina. Marque cada documento com um nível de confidencialidade e obrigue o roteador a mandar os confidenciais só para o modelo local.
Comece sem banco de grafo. Modele entidades e relações como tabelas no Postgres. GraphRAG completo é caro de indexar com um modelo local desse porte, então só vale se você provar que precisa de perguntas multi-hop.
Combine pipelines determinísticos com agente. Deixe o agente livre só para perguntas complexas, com limite de passos.
O Open WebUI deve ser só a interface. Desligue o RAG interno dele para não duplicar a lógica. Ele fala com sua API como se fosse um modelo OpenAI.

Open WebUI
    │  (API OpenAI-compatível)
    ▼

Ingestão (offline, idempotente e retomável)

PDF → hash e deduplicação → detecção de texto nativo ou escaneado → Docling (ou Marker/MinerU) com OCR de fallback → chunking por estrutura (seções e tabelas) → embeddings → Qdrant e Postgres.

Guarde página e posição de cada chunk para citar a fonte na resposta.
Use chunks pai-filho: busque no pequeno e entregue ao modelo o contexto maior.
Mantenha uma tabela ingestion_jobs com o status por documento, para retomar depois de falhas.
Para enriquecimento em massa, gere resumos por documento e por seção, não por chunk. Contextualizar 200 mil chunks com o modelo local é inviável. Se os documentos não forem sensíveis, o roteador pode mandar essa tarefa para um modelo barato no OpenRouter.
Armazenamento
Postgres é a fonte da verdade: documentos, páginas, chunks, metadados extraídos (datas, tipos, entidades, valores), tarefas, histórico e conversas. Ele permite perguntas analíticas como "quantos contratos vencem em 2027?", que busca vetorial não resolve.
Qdrant faz a busca híbrida (densa e esparsa) com filtros por metadados. O BGE-M3 gera os dois tipos de vetor e lida bem com português. Adicione um reranker (bge-reranker) depois da busca.
Arquivos originais ficam em disco ou MinIO.
Roteador

O LiteLLM Proxy é OpenAI-compatível, roteia para llama.cpp, OpenRouter e outros, faz fallback, controla orçamento e integra com o Langfuse. Uma política simples:

Tarefa	Destino
Documento confidencial	Local, sempre
Consulta simples	Local sem thinking
Raciocínio complexo em dado não sensível	Local com thinking ou modelo forte no OpenRouter
Local fora do ar ou lento	Fallback, se a política permitir

O modo thinking gasta muitos tokens. A 20 tokens/s isso pesa, então ative-o só quando fizer diferença.

Orquestração e agente

O Haystack 2.x tem pipelines de RAG e o componente Agent com tools. O Hayhooks publica pipelines e agentes como endpoints OpenAI-compatíveis. Ferramentas iniciais:

buscar_documentos, com busca híbrida e rerank
consultar_sql, somente leitura, com views controladas
ler_pagina e listar_documentos
executar_codigo, em container sem rede, com timeout e volume somente leitura
maximo_*, via MCP ou adaptador, começando só com leitura. Operações de escrita exigem confirmação humana.

Ao seu ciclo agêntico eu acrescentaria: limite de passos, validação de argumentos com Pydantic, permissões por ferramenta, citações obrigatórias na resposta final e memória de sessão no Postgres.

Observabilidade e qualidade

O Langfuse registra traces, chamadas de tools, latência e erros. Como a versão 3 exige ClickHouse, Redis e S3, reserve uns 4 a 6 GB de RAM para ele. No total cabe nos seus 64 GB: cerca de 20 GB para o modelo, Postgres e Qdrant com poucos GB cada, e o restante para o sistema e os embeddings.

Monte um conjunto de teste com 50 a 100 perguntas reais e respostas esperadas, e meça a recuperação separadamente da geração. Sem isso você não sabe se uma mudança melhorou ou piorou.

estilo esse aqui

Ver o PDF muda bastante a proposta. Este é o Diário Oficial de Montes Claros, edição 2718, com 3 colunas e várias publicações pequenas na mesma página. Ele tem texto nativo, então não precisa de OCR nesse caso. Mas o desenho gira em torno de outra coisa.

O que este tipo de documento exige

1. A unidade de indexação é o ato, não o PDF nem a página. Nesta edição há cinco atos: um Aviso de Intenção de Registro de Preços, uma Convocação, um Extrato de Termo Aditivo, um Extrato de Ratificação e um Aviso de Dispensa Eletrônica. O extrato de ratificação traz três ratificações (processos 728, 729 e 730) sob uma única assinatura, então cada ato pode ter subitens. Se você cortar em chunks de tamanho fixo, vai misturar atos diferentes.

2. A segmentação por ato é fácil de fazer com regras, porque o padrão é regular:

O ato começa com o cabeçalho "PREFEITURA MUNICIPAL DE MONTES CLAROS", seguido do título em caixa alta ou negrito.
Termina com a linha "Montes Claros, 23 de dezembro de 2024." seguida de nome e cargo do signatário.
Os subitens começam com "O Município de Montes Claros torna pública a Ratificação do PROCESSO…".
Cabeçalho e rodapé se repetem em toda página ("Terça-feira, 24 de dezembro…", "Documento assinado digitalmente…"). Remova esse ruído, junto com o sumário e o expediente da primeira página.

O risco técnico maior é a ordem de leitura em 3 colunas. Teste PyMuPDF com clusterização de colunas e o Docling em cerca de 20 edições variadas antes de processar tudo. Edições maiores provavelmente trazem leis, decretos, portarias e nomeações, com outros padrões de início e fim.

3. O processo/ano é a chave que liga os atos no tempo. Um mesmo processo aparece como aviso, convocação, resultado, ratificação e termo aditivo, em edições diferentes. Isso responde sua dúvida sobre grafo: não precisa de banco de grafo. Modele como relacional (processo → atos → entidades) no Postgres. Um grafo só entra se as perguntas multi-hop provarem a necessidade.

4. O dado é público, e isso muda o roteador. A restrição de confidencialidade que citei antes perde peso aqui. Você pode usar o OpenRouter para a extração em lote, o que ajuda muito, porque o modelo local é lento para isso. Uma conta grosseira: 200 mil atos a cerca de 10 s cada dá quase um mês de processamento local. Esse volume de atos é uma suposição minha, então meça o real na sua coleção. Se algum dia misturar documentos internos, volte à política de dados por documento.

Extração em duas camadas
Regras (regex), determinístico: número de edição e ano (do cabeçalho "ANO 12 - Nº 2718"), data, CNPJ, valores em R$, números de processo, pregão e contrato, base legal (Lei 14.133/2021), portal e ID de licitação, signatário. Seja tolerante a ruídos como "N °" e "P0620/ 24-03".
Validação cruzada: compare o valor numérico com o valor por extenso ("R$ 100.000,00 (Cem mil reais)"). Se divergirem, marque o ato para revisão.
LLM só para o que regra não resolve: normalizar o objeto, categorizar (uniformes, medicamentos veterinários, repasse de emenda parlamentar) e desambiguar entidades. Entre local e OpenRouter, decida com um conjunto de uns 100 atos rotulados por você.

No Qdrant vai um ponto por ato (ou por subitem), com payload de tipo, órgão, data, processo e entidades. Antes de gerar o embedding, coloque um cabeçalho de metadados no texto ("Extrato de Ratificação | Secretaria de Saúde | 24/12/2024 | Processo 728/2024"). É contextualização sem gastar LLM.

Por que a busca híbrida é obrigatória

Perguntas com "Processo 728/2024", um CNPJ ou o nome de uma pessoa falham com busca só vetorial. Combine filtro exato no Postgres, busca esparsa (BM25/SPLADE) e vetorial, mais o reranker.

Como os atos são curtos (algumas centenas de tokens), um contexto RAG de 10 atos tem cerca de 4 mil tokens. Isso alivia o gargalo de prefill do modelo local, e ele fica bem para uso interativo.

O que isso muda no projeto
Triagem por página antes de tudo. Cada página é classificada como texto ok, corrompido ou escaneado. Uso como critério a razão de palavras legíveis e fontes sem Unicode, e você ajusta os limites com seus dados. Páginas ruins vão para OCR. O Tesseract que testei já foi bom em placas e datas, e com o modelo por recupera os acentos. Grave em cada página o método usado e a qualidade.
OCR de tabela precisa de validação por padrão. O Tesseract leu FFN0E84 como FFNOE84. Na placa Mercosul a 4ª posição é dígito, então dá para corrigir O→0 por regra. Valide também o CNPJ pelo dígito verificador, o valor numérico contra o valor por extenso, e as datas contra a edição. Para buscar placa ou nome, use similaridade por trigramas no Postgres. O modelo multimodal (o Qwen3.6 aceita imagem) fica só como verificação das páginas de baixa confiança, porque é lento demais para milhares de linhas.
Ordem de leitura por colunas detectadas, não fixas. Os atos atravessam colunas e páginas. Um exemplo é o Extrato 189/2026, em que o valor "R$ 1.638,00" cai na coluna seguinte. Além disso, a ordem do fluxo interno do PDF não é a ordem visual.
Segmentação por cabeçalho e assinatura. Os cabeçalhos variam ("Prefeitura De Montes Claros/MG", "Município de Montes Claros – MG / Procuradoria-Geral", "MCTRANS"). Os atos terminam na linha de data e assinatura, e as barras de seção (Prefeitura, Câmara, PREVMOC) viram metadado. Atos com vários itens, como a Ata 150/2026 (5 atas) e o Extrato 174/2026 (3 contratos), precisam de uma tabela ato_itens. O que a regra não classificar vai para uma fila de revisão, não é descartado.
Valores e datas tipados. Somar "valores" não faz sentido nesse material. O Extrato 823 acresce e decresce os mesmos R$ 130.206,19 sem mudar o valor global. O 170 traz acréscimo de R$ 91.537,50 e novo valor global de R$ 756.227,50. O 788 retifica um acréscimo anterior. Use tipos como acrescimo, decrescimo, valor_global_novo e valor_estimado. Faça o mesmo com as datas (publicação, assinatura, ratificação, efeitos, sessão), porque o aditivo 769 retroage efeitos a 10/07/2026.
Referências entre atos. Ligue aditivo ao contrato, ratificação ao processo e retificação ao ato corrigido. A retificação de 11/08 cita a edição 3084, página 2. As chaves são processo, modalidade, contrato (P0177/26-01), ata e número do extrato. O "Processo Administrativo Digital" é outro número, diferente do processo licitatório.
Dados pessoais. A lista da PREVMOC mascara o CPF, mas traz nome e matrícula. O decreto de 20/08 publica um CPF completo. As listas de numeração trazem nomes de cidadãos com endereço. Mascare o CPF na ingestão, mantenha esses atos só no modelo local e não os mande ao OpenRouter. Não sou advogado, então vale confirmar a leitura de LGPD.
Erros da própria fonte. O Diário tem "INEXIBILIDADE", CNPJ mal formatado (51.490.695-0001/78) e uma dispensa de 2026 numerada como "029/2023". Normalize com correspondência aproximada, marque a qualidade do dado e faça o agente responder "conforme publicado". Os aditivos também truncam a tabela de itens com "(...)", então algumas respostas simplesmente não estão no Diário.
